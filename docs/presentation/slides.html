01 — OVERVIEW

프로젝트 개요

  • 4인 텍사스 홀덤 웹 게임 — 회원가입 없이 닉네임만으로 즉시 플레이
  • 실시간 멀티플레이어 — WebSocket 양방향 통신, 20초 턴 타이머
  • 다중 테이블 — 여러 게임이 동시 진행
  • 스택: Node.js(ws) + React + Redis

이 발표의 초점

게임을 AWS 위에서 어떻게 확장 가능하고 안정적으로 운영하는가 — 컨테이너 오케스트레이션, 상태 관리, 오토스케일링

02 — REQUIREMENTS

게임 서버의 인프라 요구사항

  • 실시간 양방향 통신 — HTTP 폴링이 아닌 WebSocket, 연결이 오래 유지되어야 함
  • 수평 확장 — 동시 접속이 늘면 서버를 늘려야 함 (Auto Scaling)
  • 서버 장애 ≠ 게임 증발 — 어떤 서버가 죽어도 게임 상태는 보존
  • 분산 환경의 일관성 — 같은 게임의 4명이 서로 다른 서버에 붙어도 동작

핵심 설계 결정

서버를 완전한 Stateless로 만들고, 게임 상태는 전부 ElastiCache Redis에 둔다
→ sticky session 불필요, 어느 컨테이너든 어느 플레이어든 처리 가능

04 — WHY ECS

왜 ECS(EC2)인가 — EKS에서 전환한 이유

처음 계획: EKS (Kubernetes)

  • 컨트롤 플레인 비용 $73/월 고정 — 워커 노드와 별도
  • 학습 곡선: 매니페스트, Helm, IRSA…
  • 4인 게임 서버 2~4개에는 과한 복잡도

전환: ECS on EC2

  • 클러스터 관리 무료 — 컨테이너 비용만
  • ALB·ASG·CloudWatch와 네이티브 통합
  • Task Definition 하나로 배포 정의 끝
  • Fargate 대신 EC2 — 비용 절감 + ASG 직접 제어

교훈: 기술 선택은 "유행"이 아니라 규모와 팀에 맞는 복잡도로

05 — STATE MANAGEMENT

Stateless 서버 + ElastiCache Redis

  • 게임 상태 전부 Redis에 — 카드, 팟, 턴, 타이머 deadline까지
  • Pub/Sub로 게임 이벤트 브로드캐스트 — 다른 태스크에 붙은 플레이어에게도 전달
  • Lua 스크립트로 조회+검증+업데이트 원자 실행 — race condition 방어
  • 턴 타이머: turn_deadline 키 1초 폴링 → 만료 시 auto-fold

실제로 검증한 시나리오

4명의 클라이언트가 ALB를 거쳐 서로 다른 ECS 태스크에 분산 접속 → 프리플랍부터 쇼다운까지 풀 게임 완주 ✓

= Redis 상태 공유와 크로스 인스턴스 Pub/Sub이 프로덕션에서 동작함을 증명

06 — DEPLOYMENT

컨테이너 배포 파이프라인

Dockerfile (node:20-alpine, 56MB)  →  ECR push  →  Task Definition 등록  →  ECS Service 롤링 배포
  • awsvpc 네트워크 모드 — 태스크마다 자체 ENI/IP, SG를 태스크 단위로 적용
  • 롤링 배포: minimumHealthy 100% / maximum 200% — 무중단, 새 태스크 healthy 후 구버전 종료
  • 컨테이너 헬스체크 + ALB /health 헬스체크 이중화
  • 재배포 = 이미지 push 후 update-service --force-new-deployment 한 줄
07 — TRAFFIC

ALB — WebSocket을 위한 설정

  • idle timeout 3600초 — 기본 60초면 게임 중 WebSocket이 끊김. 가장 중요한 한 줄
  • target-type: ip — awsvpc 모드 태스크의 ENI로 직접 라우팅
  • 헬스체크: GET /health 30초 간격, healthy 2회 / unhealthy 3회
  • HTTP 80 리스너 → 타깃 그룹 포워딩 — ws:// 업그레이드는 ALB가 네이티브 지원

왜 NLB가 아니라 ALB?

L7 헬스체크(경로 기반)와 WebSocket 업그레이드 처리, 추후 경로 라우팅 확장성 — 게임 트래픽 규모에서는 ALB가 운영상 단순

08 — AUTO SCALING

2단 Auto Scaling

① 서비스 레벨 (Application Auto Scaling)

  • ECS Service 태스크 수: 2 ~ 8개
  • CPU 70% 타깃 트래킹
  • scale-out 60s / scale-in 300s 쿨다운

② 인프라 레벨 (Capacity Provider)

  • ASG: t3.small 2 ~ 4대
  • 타깃 capacity 80% — 태스크가 못 들어가면 EC2 자동 증설
  • 관리형 스케일링: ECS가 ASG를 직접 조정

동작 흐름

트래픽 증가
→ 태스크 CPU 70% 초과
→ 태스크 증설 (서비스 레벨)
→ EC2에 빈 자리 부족
→ EC2 증설 (Capacity Provider)

반대로 한가하면 역순으로 축소 — 실습 중 비용 절약을 위해 desired 0으로 내려두기도

09 — SECURITY

최소 권한 설계

🔒 ALB-SG (80 ← 인터넷)  →  EC2-SG (3001 ← ALB-SG만)  →  Redis-SG (6379 ← EC2-SG만)
  • 보안 그룹 참조 체인 — IP가 아닌 SG 참조로 인바운드 제한. Redis는 인터넷에서 도달 불가
  • IAM 역할 3종 분리
    Task Role(S3 쓰기만) / Execution Role(ECR pull·로그) / Instance Role(ECS 등록)
  • IAM 사용자도 최소 권한 — 필요한 액션만 명시한 정책 파일을 관리하며 점진적으로 요청
    예: CreateLoadBalancer의 숨은 의존 권한(ec2:DescribeAccountAttributes)을 실패 → 분석 → 추가로 해결
10 — VERIFICATION

검증 — "되는 것 같다"가 아니라 증명

  • 단위/통합 테스트 44개 — 게임 엔진(핸드 판정, 베팅 라운드), Redis 타이머, WS 연결 종료 처리
  • 로컬 E2E: 실제 브라우저 4개 자동 조작 → 풀 게임 완주 (Playwright)
  • 프로덕션 E2E: ALB 경유 4클라이언트 시뮬레이션 → 멀티 태스크 분산 환경에서 쇼다운까지 완주
  • ALB 헬스체크 OK · 타깃 2/2 healthy · 롤링 배포 무중단 확인

TDD로 잡은 실제 버그들

베팅 라운드 종료 판정 누락(게임이 플랍을 못 봄) · 턴 타이머 TTL이 deadline과 동시 만료(auto-fold 불능) · 쇼다운 키커 무시(A페어=K페어 무승부) · 연결 끊김 시 유령 방 잔류
