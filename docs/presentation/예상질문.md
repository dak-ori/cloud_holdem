# 예상 질문 & 답변 준비

## 인프라 설계

**Q1. 왜 Fargate가 아니라 EC2 타입을 썼나요?**
> Fargate는 vCPU·메모리 단가가 EC2보다 높아서, 상시 실행되는 서비스는 EC2가 저렴합니다. t3.small 2대가 동급 Fargate 대비 약 40% 쌉니다. 또 Capacity Provider와 ASG를 직접 구성해보는 학습 목적도 있었습니다. 트래픽이 매우 불규칙하다면 Fargate(특히 Spot)가 나을 수 있습니다.

**Q2. 서버(태스크)가 죽으면 진행 중인 게임은 어떻게 되나요?**
> 게임 상태가 전부 Redis에 있어서 사라지지 않습니다. ALB가 unhealthy 타깃을 제외하고, 클라이언트는 exponential backoff로 자동 재연결해 다른 태스크에 붙습니다. ECS 서비스가 desired count를 유지하므로 죽은 태스크는 자동으로 대체됩니다.

**Q3. 그럼 Redis가 죽으면요? (단일 장애점 아닌가요?)**
> 맞습니다. 현재는 비용 때문에 single-node라 Redis가 SPOF입니다. 실서비스라면 ElastiCache Multi-AZ 복제(자동 failover)나 Redis Cluster로 개선해야 합니다. 이번 프로젝트에서는 의도적으로 받아들인 트레이드오프입니다.

**Q4. sticky session 없이 WebSocket이 어떻게 동작하나요?**
> WebSocket 연결 자체는 특정 태스크에 붙지만, 상태가 서버에 없어서 "어느 태스크에 붙는지"가 중요하지 않습니다. 같은 게임의 다른 플레이어가 다른 태스크에 있어도 Redis Pub/Sub으로 이벤트가 모든 태스크에 전파됩니다.

**Q5. 스케일 인(축소)될 때 기존 WebSocket 연결은 끊기지 않나요?**
> 끊깁니다. 다만 클라이언트가 자동 재연결하고 상태는 Redis에 있으므로 게임은 계속됩니다. 개선하려면 ALB connection draining 시간을 늘리거나, 종료 예정 태스크가 신규 연결만 거부하게 할 수 있습니다.

**Q6. race condition은 구체적으로 어떤 상황이고 어떻게 막았나요?**
> 예: 플레이어 액션과 턴 타이머 만료(auto-fold)가 동시에 도착하는 경우. Redis Lua 스크립트로 "상태 조회 → 현재 턴 검증 → 저장"을 원자적으로 실행해서, 검증 시점과 저장 시점 사이에 다른 변경이 끼어들 수 없게 했습니다.

**Q7. HTTPS/WSS가 아니라 HTTP/WS인 이유는?**
> 실습 범위 제한입니다. 실서비스라면 ACM 무료 인증서 + ALB 443 리스너 + S3 앞에 CloudFront를 붙여 HTTPS/WSS로 전환합니다. 구조 변경 없이 리스너/도메인 설정만 추가하면 됩니다.

**Q8. 비용을 더 줄이려면?**
> ① EC2 Spot 인스턴스(stateless라 중단 내성 있음) ② Graviton(t4g) 전환 ③ 야간 자동 축소 스케줄 ④ 트래픽이 거의 없으면 단일 노드 구성. 실습 중에도 안 쓸 때 ASG desired 0으로 내려 비용을 아꼈습니다.

**Q9. CI/CD는 없나요?**
> 현재는 스크립트 기반 수동 배포입니다. GitHub Actions로 push → 테스트 → ECR push → `update-service --force-new-deployment`를 자동화하는 게 다음 단계입니다.

**Q10. 모니터링은 어떻게 하나요?**
> CloudWatch Logs(awslogs 드라이버)로 컨테이너 로그 수집, 타깃 트래킹이 만든 CPU 알람 2개가 동작 중입니다. 개선한다면 ALB 5xx/타깃 unhealthy 알람과 대시보드를 추가하겠습니다.

## 게임/애플리케이션

**Q11. 다른 사람 카드를 훔쳐볼 수 있지 않나요? (치팅)**
> 카드 정보는 서버(Redis)에만 있고, 각 클라이언트에는 자기 카드와 공개된 커뮤니티 카드만 전송합니다. 클라이언트를 조작해도 받은 데이터에 상대 카드가 없습니다.

**Q12. 동시에 몇 개 테이블까지 가능한가요?**
> 게임 하나의 상태는 수 KB라 Redis 용량은 사실상 무제한이고, 병목은 태스크당 WebSocket 연결 수입니다. Node.js 태스크 하나가 수천 연결을 처리하고, 부족하면 오토스케일링으로 태스크가 늘어나는 구조입니다.

**Q13. 테스트는 어떻게 했나요?**
> 게임 엔진(핸드 평가, 베팅 라운드, 팟 분배)과 Redis 로직에 단위·통합 테스트 44개를 TDD로 작성했고, Playwright로 브라우저 4개를 자동 조작하는 E2E, 마지막으로 프로덕션 ALB에 4클라이언트 시뮬레이션을 돌려 분산 환경을 검증했습니다.

**Q14. 가장 어려웠던 버그는?**
> 턴 타이머 버그입니다. Redis 키의 TTL을 마감 시각과 똑같이 설정해서, 폴러가 "만료된 deadline"을 읽으려는 순간 키가 이미 사라져 auto-fold가 영원히 발동하지 않았습니다. TTL에 여유분을 두는 한 줄로 고쳤지만, 원인을 찾는 과정에서 분산 타이머 설계를 제대로 이해하게 됐습니다.
